# Instructions for AI Agents – Creating and Managing Course Lectures

This document defines the structure, conventions, pedagogical requirements, session-handling workflow, and formatting rules for creating or editing lecture files in this course.

## Primary Reference Files

Before creating or modifying any lecture, always inspect the following files:

1. `.COURSE_PLAN_SUMMARY.md`

   * Course plan
   * Syllabus units
   * Lecture schedule
   * Course Outcomes (COs)
   * Assessment details
   * Lecture sequence

2. `.Course_Session_handelling_{subjectname}.xlsx`

   * Official course session-handling record
   * Lecture-wise implementation plan
   * CO mapping
   * Knowledge levels
   * Skills
   * Applications
   * PBL activities
   * Assessment planning

The lecture number, unit, topic, and CO must remain consistent across all these files.

---

# Course Session Implementation Framework

Every lecture must be designed and documented in alignment with the following academic dimensions:

| Dimension           | Purpose                                                                       |
| ------------------- | ----------------------------------------------------------------------------- |
| Course Outcome (CO) | Defines the measurable learning outcome addressed by the lecture              |
| Knowledge Level     | Maps learning to Bloom's Taxonomy                                             |
| Skills              | Identifies technical, analytical, practical, or professional skills developed |
| Applications        | Connects concepts with real-world or industrial applications                  |
| PBL Activity        | Defines problem-based or project-based learning activity                      |
| Assessment          | Defines how learning and CO attainment will be evaluated                      |

These dimensions must be considered while creating the lecture content, not added merely as documentation.

---

# Mandatory Lecture Planning Table

Every lecture file must contain a lecture implementation table immediately after the lecture title and Course Outcome.

Use the following structure:

```markdown
## Session Implementation Plan

| Parameter | Details |
|---|---|
| Lecture No. | {NN} |
| Unit | {Unit Number and Name} |
| Topic | {Lecture Topic} |
| Course Outcome | CO{N} – {CO statement} |
| Bloom's Knowledge Level | {Remember / Understand / Apply / Analyze / Evaluate / Create} |
| Skills Developed | {Technical, analytical, programming, problem-solving, communication, etc.} |
| Applications | {Real-world, industrial, academic, or practical application} |
| PBL Activity | {Problem, case study, design task, mini-project, investigation, etc.} |
| Assessment Method | {Quiz, coding task, viva, assignment, rubric, peer review, etc.} |
```

## Rules for Session Implementation Table

1. Every lecture must contain this table.
2. Values must correspond to the course session-handling Excel file.
3. The table must be meaningful and lecture-specific.
4. Do not use generic values such as "Programming Skills" for every lecture.
5. Skills must reflect what students actually practice during that session.
6. Applications must connect the topic to realistic use cases.
7. PBL activities should progressively contribute toward problem-solving or project development where possible.
8. Assessment must evaluate the intended knowledge level and CO.

# Bloom's Taxonomy Mapping Rules

Use appropriate Bloom's Taxonomy levels when designing lectures.

| Level      | Typical Student Activities                | Suitable Assessment          |
| ---------- | ----------------------------------------- | ---------------------------- |
| Remember   | Recall definitions, syntax, facts         | Quiz, MCQ                    |
| Understand | Explain concepts and relationships        | Short answer, discussion     |
| Apply      | Use concepts to solve problems            | Programming task, exercise   |
| Analyze    | Compare, debug, investigate               | Case study, debugging task   |
| Evaluate   | Justify decisions or compare alternatives | Review, design evaluation    |
| Create     | Design and build a solution               | Project, PBL, implementation |

## Important Rule

The knowledge level must match the actual learning activity.

For example:

* A lecture explaining HTTP concepts should primarily target Remembering and Understanding.
* A lecture implementing REST APIs should target Applying.
* A lecture debugging API failures should target Analyzing.
* A lecture designing a backend architecture should target Creating.

Do not assign advanced Bloom's levels unless the lecture actually includes activities supporting those levels.

# Skills Mapping Rules

For every lecture, explicitly identify the skills students develop.

Possible categories include:

* Conceptual understanding
* Logical thinking
* Problem-solving
* Programming
* Debugging
* System design
* API development
* Database design
* Testing
* Documentation
* Collaboration
* Communication
* Tool usage
* Analytical thinking

Skills must be specific to the lecture.

Example:

| Weak            | Preferred                                                    |
| --------------- | ------------------------------------------------------------ |
| Programming     | Writing and testing asynchronous Express.js routes           |
| Problem solving | Identifying and fixing HTTP request-response failures        |
| Database skills | Designing MongoDB collections and performing CRUD operations |

---

# Application Mapping Rules

Each lecture must explain where the concept is used.

Applications may include:

* Industry systems
* Web applications
* Enterprise software
* Cloud platforms
* IoT systems
* Mobile backends
* Automation
* Data processing
* Security systems
* Research applications

Example:

```markdown
Applications:
REST APIs are used in mobile applications, web applications, microservices,
payment gateways, IoT platforms, and third-party service integrations.
```

Avoid vague statements such as:

```text
Used in software development.
```

Prefer specific application contexts.

---

# Problem-Based Learning (PBL) Rules

Each lecture should include a suitable PBL activity where appropriate.

PBL activities can include:

1. Problem identification
2. Case study analysis
3. Debugging challenge
4. System design challenge
5. Mini-project task
6. Real-world scenario
7. Team discussion
8. Comparative analysis
9. Investigation activity

PBL activities should ideally build progressively across lectures.

Example progression:

```text
Lecture 01
Understand the problem domain.

Lecture 02
Analyze client-server interaction.

Lecture 03
Set up the development environment.

Lecture 04
Build the first API.

Lecture 05
Extend the API with CRUD operations.

Lecture 06
Debug and test the application.

Lecture 07
Design a complete backend module.
```

The objective is to gradually move students from understanding toward application and creation.

# Assessment Planning Rules

Every lecture must specify an assessment mechanism aligned with the CO and Bloom's level.

Possible assessment methods:

* MCQ Quiz
* Short answer questions
* Coding exercise
* Hands-on implementation
* Debugging challenge
* Assignment
* Viva
* Case study
* Peer review
* Demonstration
* Mini-project evaluation

## Alignment Rule

Assessment must evaluate the same knowledge level targeted by the lecture.

Example:

| Knowledge Level | Suitable Assessment       |
| --------------- | ------------------------- |
| Remember        | MCQ                       |
| Understand      | Explain concept           |
| Apply           | Coding exercise           |
| Analyze         | Debugging task            |
| Evaluate        | Comparative justification |
| Create          | Project implementation    |

Avoid using only quizzes for lectures focused on practical skill development.

# Course Session-Handling Excel File Management

A hidden or dot-prefixed Excel file must be maintained in the root directory of the course repository.

## Naming Convention

The file must use the following format:

```text
.Course_Session_handelling_{subjectname}.xlsx
```

Examples:

```text
.Course_Session_handelling_Backend_Development.xlsx
.Course_Session_handelling_Python_Programming.xlsx
.Course_Session_handelling_DevOps.xlsx
```

Use underscores or a consistent repository-safe naming format for multi-word subject names.

---

# Excel File Location

The session-handling Excel file must always remain in the root directory.

Example repository structure:

```text
course-repository/
│
├── .AGENTS.md
├── .COURSE_PLAN_SUMMARY.md
├── .Course_Session_handelling_Backend_Development.xlsx
│
├── Theory/
│   ├── L01 Overview.md
│   ├── L02 Architecture.md
│   └── ...
│
├── Lab/
│   ├── Exp 01 Introduction.md
│   └── ...
│
└── list.txt
```

Do not move the Excel file into the Theory or Lab directory.

# Excel Update Workflow

The Excel file must be updated whenever any of the following actions occur:

1. A new lecture file is created.
2. A lecture topic is modified.
3. A lecture is moved to another unit.
4. CO mapping changes.
5. Bloom's knowledge level changes.
6. Skills are modified.
7. Application context changes.
8. PBL activity is added or modified.
9. Assessment method changes.
10. Lecture sequence is modified.

## Mandatory Agent Workflow

Whenever modifying lecture content:

```text
Step 1
Read .COURSE_PLAN_SUMMARY.md.

Step 2
Identify lecture number, unit, topic, and CO.

Step 3
Determine appropriate Bloom's knowledge level.

Step 4
Identify measurable skills developed.

Step 5
Identify realistic applications.

Step 6
Design or update PBL activity.

Step 7
Define assessment aligned with CO and Bloom's level.

Step 8
Create or modify the lecture Markdown file.

Step 9
Update the Session Implementation Plan inside the lecture.

Step 10
Update .Course_Session_handelling_{subjectname}.xlsx.

Step 11
Verify consistency between:
- Course plan
- Lecture Markdown
- First presentation slide
- Session-handling Excel file

Step 12
Update list.txt if a new lecture file was created.
```

# Pedagogical Progression Rules

Lecture sessions should progressively move through:

```text
Knowledge
    ↓
Understanding
    ↓
Application
    ↓
Analysis
    ↓
Evaluation
    ↓
Creation
```

A complete unit should not consist entirely of Remembering and Understanding activities.

Where appropriate, later lectures in a unit should increase cognitive complexity.

Recommended progression:

| Lecture Stage            | Preferred Bloom's Levels |
| ------------------------ | ------------------------ |
| Introduction             | Remember, Understand     |
| Core Concepts            | Understand, Apply        |
| Practical Implementation | Apply                    |
| Troubleshooting          | Analyze                  |
| Design Decisions         | Evaluate                 |
| Project/PBL              | Create                   |

        ↕
Lecture File

# Critical Agent Rule

Whenever a lecture is created or modified, the task is NOT complete until the corresponding row in:

```text
.Course_Session_handelling_{subjectname}.xlsx
```

has also been created or updated.

The Excel file is the authoritative session implementation record and must always reflect the latest state of the course repository.
