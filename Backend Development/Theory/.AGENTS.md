# Instructions for AI Agents – Creating Lecture Files

This document defines the structure, conventions, and formatting rules for creating or editing lecture files in this course.

**Reference:** See `.COURSE_PLAN_SUMMARY.md` for the full course plan, syllabus units, lecture schedule, course outcomes, and assessment details. When creating a lecture, map it to the correct unit and lecture number from that file.

---

## File Naming Convention

```
L{NN} {Topic Title}.md
```

Examples:

- `L01 Overview of Backend Development.md`
- `L02 Client–Server Architecture.md`
- `L03 Setting Up the Backend Environment.md`

Always use the format: `L` + two-digit number + space + descriptive title. File extension is `.md`.

---

## Lecture File Structure

Every lecture file **must** follow this structure:

```markdown
# Lecture {NN}

# {Lecture Title}

**Course Outcome:** CO{N} – {one-line outcome statement}.

---

## Part A – Theory

---

### 1. Introduction

{Brief intro linking to previous lectures and stating what students will learn today.}

By the end of this lecture, you will have:

1. {learning outcome 1}
2. {learning outcome 2}
3. {learning outcome 3}

---

### {N}. {Theory Topic}

{Content here}

---

## Part B – Installation

---

### {N}. {Installation Step}

{Only include if the lecture requires tool installation. Skip this part if not needed.}

---

## Part C – Hands-On: {Title}

---

### {N}. Task {N} — {Task Title}

#### Step {N}: {Step description}

{Code block}

{Expected output}

{Testing instructions with URL or command}

---

## {N}. Summary

{Bulleted recap of everything covered}

### Key Takeaways

* {takeaway 1}
* {takeaway 2}
* {takeaway 3}

---

### Lab Exercise

1. {exercise 1}
2. {exercise 2}
3. {exercise 3}
```

## Section Rules

### Theory Section (Part A)

- Always start with **Part A – Theory**.
- Number sections sequentially starting from `1.` (Introduction).
- Each theory topic gets its own `###` heading.
- Use **bold** for defining key terms on first mention.
- Use bullet points for lists of features, characteristics, or benefits.
- Use tables for comparing items (e.g., HTTP methods, status codes, protocols).
- End theory with a transition paragraph linking to the hands-on section.

### Installation Section (Part B)

- Include only when new software or tools are required.
- Provide step-by-step instructions with exact commands.
- Include verification commands with expected output.
- Cover all platforms (Windows, macOS/Linux) where commands differ.

### Hands-On Section (Part C)

- Every hands-on section **must** have at least 3 incremental tasks.
- Tasks must build on each other — each task extends the previous one.
- Every task must include:
  - A descriptive title.
  - Numbered steps.
  - Complete, runnable code snippets (not fragments).
  - Expected output or result.
  - A way to test (browser URL, curl command, or Postman).
- Use real-world examples (Student Management API, Library API, etc.).

### Summary Section

- Start with a numbered recap of key concepts.
- Include a **Key Takeaways** sub-section with bullet points.
- End with a transition sentence linking to the next lecture.

### Lab Exercise Section

- Always include 3–5 exercises.
- Mix of modification tasks (extend existing code) and observation tasks (use DevTools, Postman).
- At least one exercise should require writing new code independently.

## Diagrams and Illustrations – SVG Rule

**All diagrams, illustrations, flowcharts, and architecture visuals MUST be created using inline SVG code.** Do not use external image files (PNG, JPG, GIF) or image links.

### Why Inline SVG

- Renders directly in GitHub markdown and any browser.
- No external dependencies or broken image links.
- Can be styled with colors, fonts, and shapes.
- Version-controlled alongside the lecture content.

### SVG Template

Use this base template for diagrams:

```html
<svg xmlns="http://www.w3.org/2000/svg" width="{WIDTH}" height="{HEIGHT}" viewBox="0 0 {WIDTH} {HEIGHT}">
<rect width="{WIDTH}" height="{HEIGHT}" fill="white"/>

<!-- Components -->
<rect x="{X}" y="{Y}" width="{W}" height="{H}" rx="8" fill="{COLOR}" stroke="{STROKE}"/>
<text x="{CENTER_X}" y="{TEXT_Y}" text-anchor="middle" font-size="18">{Label}</text>

<!-- Arrows -->
<line x1="{X1}" y1="{Y1}" x2="{X2}" y2="{Y2}" stroke="black" stroke-width="2"/>
<polygon points="{PT1} {PT2} {PT3}" fill="black"/>
</svg>
```

### Color Palette for Components

Use consistent colors across all lectures:

| Component Type | Fill Color | Stroke Color |
|---------------|------------|--------------|
| Client / Browser | `#EAF4FF` | `#1E88E5` |
| Server / Backend | `#E8F8EC` | `#43A047` |
| Database / Storage | `#FFF8E6` | `#FB8C00` |
| External Service | `#F3E5F5` | `#8E24AA` |
| User / Actor | `#FCE4EC` | `#E53935` |
| Process / Action | `#E0F7FA` | `#00ACC1` |

### SVG Rules

1. **Width:** Use `800`–`900` pixels for standard diagrams. Use `600` for smaller ones.
2. **Height:** Adjust based on content. Typical range: `200`–`400`.
3. **Background:** Always include a white background rect.
4. **Rounded corners:** Use `rx="8"` on all component rectangles.
5. **Font sizes:** `18`–`20` for titles, `13`–`14` for descriptions.
6. **Arrows:** Use `stroke-width="2"` with filled triangular arrowheads.
7. **Labels on arrows:** Place text at midpoint of the line, offset slightly above (`y - 15`).
8. **Text alignment:** Always use `text-anchor="middle"` for centered text.

### Example: Request–Response Diagram

```html
<svg xmlns="http://www.w3.org/2000/svg" width="800" height="200" viewBox="0 0 800 200">
<rect width="800" height="200" fill="white"/>

<rect x="40" y="50" width="180" height="100" rx="8" fill="#EAF4FF" stroke="#1E88E5"/>
<text x="130" y="80" text-anchor="middle" font-size="20">Client</text>
<text x="130" y="105" text-anchor="middle" font-size="14">Browser</text>

<rect x="580" y="50" width="180" height="100" rx="8" fill="#E8F8EC" stroke="#43A047"/>
<text x="670" y="80" text-anchor="middle" font-size="20">Server</text>
<text x="670" y="105" text-anchor="middle" font-size="14">Express / Flask</text>

<line x1="220" y1="80" x2="580" y2="80" stroke="black" stroke-width="2"/>
<polygon points="575,75 588,80 575,85" fill="black"/>
<text x="400" y="70" text-anchor="middle" font-size="13">HTTP Request</text>

<line x1="580" y1="120" x2="220" y2="120" stroke="black" stroke-width="2"/>
<polygon points="225,115 212,120 225,125" fill="black"/>
<text x="400" y="140" text-anchor="middle" font-size="13">HTTP Response</text>
</svg>
```

### When to Use Diagrams

Include an SVG diagram in these situations:

- Architecture overview (client–server, three-tier, microservices)
- Request–response flow
- Data flow between components
- Project directory structure
- Process sequence (login flow, authentication flow)
- Comparison diagrams (REST vs GraphQL, SQL vs NoSQL)

Do **not** use diagrams for:

- Simple code output
- Lists that are already clear as bullet points
- Tables with fewer than 3 rows

## Code Snippet Rules

1. Always specify the language after the triple backtick: ` ```javascript `, ` ```python `, ` ```bash `.
2. Code must be complete and runnable — no placeholders like `# ... rest of code`.
3. Use realistic variable names and example data (student names, course names).
4. Include comments only when a line is non-obvious.
5. For multi-file projects, clearly label which file each code block belongs to.
6. Show expected output in a separate code block after the code.

---

## Content Guidelines

- **Tone:** Academic but approachable. Write as if explaining to a motivated student.
- **Previous lecture references:** Always link back to the previous lecture in the Introduction.
- **Next lecture preview:** Always end the Summary with a sentence pointing to the next lecture.
- **Examples:** Use a consistent running project across lectures (e.g., Student Management System).
- **Terminology:** Define technical terms on first use with **bold**.
- **Sentences:** Keep sentences under 25 words where possible.
- **Tables:** Use for any comparison of 3+ items.
- **Horizontal rules:** Use `---` between major sections for visual separation.

- [ ] Course outcome line is present.

- [ ] All diagrams use inline SVG, not image files.

- [ ] Code snippets specify language and are complete/runnable.
- [ ] Summary and Key Takeaways are present.
