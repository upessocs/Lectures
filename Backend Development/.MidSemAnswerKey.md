## Q1. Explain session management and justify its need in web applications. (6 Marks)

### Suggestive answer

Session management is the process of maintaining information about a user's interaction with a web application across multiple HTTP requests.

HTTP is stateless, meaning each request is independent by default. Session management allows the application to recognize a user and retain relevant information between requests.

Need for session management:

- Authentication: Maintains the authenticated user's state after login.
- Personalization: Stores preferences, language, or theme settings.
- Shopping carts: Maintains selected products across multiple pages.
- Access control: Helps restrict access to authorized users.
- Continuity: Preserves relevant application state during navigation.

Working mechanism:

1. A user logs in with valid credentials.
2. The server creates a session and generates a session identifier.
3. The identifier is commonly sent to the browser in a cookie.
4. The browser sends the cookie with subsequent requests.
5. The server identifies the session and retrieves the associated information.
6. The session is invalidated on logout or expiry.

## Q6. Explain the principles of RESTful APIs. Justify whether HTTP is stateless, using a suitable request-response example. (15 Marks)

### Suggestive answer

REST (Representational State Transfer) is an architectural style for designing networked applications. A RESTful API exposes resources through identifiable URIs and uses standard HTTP methods to interact with them.

### A. Principles of RESTful APIs (9 Marks)

1. Client-server separation: The client handles the user interface; the server handles data and business logic.
2. Stateless communication: Each request contains the information necessary to process it. The server does not depend on stored conversational context from previous requests.
3. Uniform interface: Resources are identified by URIs and accessed through consistent methods and representations.
4. Resource-based design: Resources such as students are represented by URIs, for example `/api/students/101`.
5. HTTP methods: `GET` retrieves data, `POST` creates or submits data, `PUT` replaces a resource, `PATCH` partially updates it, and `DELETE` removes it.
6. Cacheability: Responses should indicate whether they may be cached.
7. Layered system: Clients need not know whether they communicate directly with the application server or through intermediaries.
8. Representations: Resources can be represented in JSON, XML, or other suitable formats.
9. Code on demand (optional): A server may provide executable code to a client; this is an optional REST constraint.

### B. Is HTTP stateless? (3 Marks)

HTTP is stateless at the protocol level. Each HTTP request is treated independently; HTTP itself does not automatically preserve application-session context between requests.

For example:

```
GET /api/students/101 HTTP/1.1
Host: example.com
Accept: application/json
```

The server processes the request and may return:

```
HTTP/1.1 200 OK
Content-Type: application/json
```

```
{
  "id": 101,
  "name": "Amit"
}
```

A subsequent request must independently provide the information required to process it. The server does not automatically know the context of the earlier request merely because it occurred first.

### C. Statelessness versus session management (3 Marks)

A web application can implement sessions using cookies or tokens, even though HTTP itself is stateless.

For example, an authenticated request might include:

```
GET /api/profile HTTP/1.1
Host: example.com
Cookie: sessionId=abc123
```

The server can use the cookie to identify a session. This does not make HTTP inherently stateful; it is an application-level mechanism built on top of HTTP.

In a strictly stateless REST interaction, the server should not depend on conversational session state to interpret the request.

## Q7. Analyze client-server architecture. Illustrate the roles of the client and server and their request-response interaction with a suitable diagram. (15 Marks)

### Suggestive answer

Client-server architecture is a distributed computing model in which a client requests services or resources and a server processes requests and returns responses.

### A. Roles of client and server (5 Marks)

Client:

- Provides the user interface.
- Accepts user input.
- Sends HTTP requests to the server.
- Processes returned data and displays results.
- May perform client-side validation and rendering.

Examples include web browsers, mobile applications, and frontend JavaScript applications.

Server:

- Accepts and processes client requests.
- Executes business logic and validation.
- Interacts with databases or external services.
- Applies authentication and authorization.
- Returns responses with status codes, headers, and content.

Examples include Node.js/Express, Django, and other web server applications.

### B. Request-response diagram (5 Marks)

### C. Request-response workflow (3 Marks)

1. The user performs an action in the browser.
2. The browser constructs and sends an HTTP request.
3. The server routes and validates the request.
4. The application performs the required logic and may query the database.
5. The server generates an HTTP response.
6. The browser processes the response and updates the interface.

### D. Analysis: advantages and limitations (2 Marks)

Advantages:

- Centralized data and business logic.
- Easier maintenance and controlled access.
- Multiple clients can use the same backend services.

Limitations:

- Server downtime can affect multiple clients.
- Network latency affects response time.
- High request volumes may require load balancing and horizontal scaling.

## Q8. Server-Side Rendering (SSR) (5 + 10 = 15 Marks)

### Q8(a). Explain SSR and state two benefits. (5 Marks)

Suggestive answer

Server-Side Rendering (SSR) is a technique in which the server generates HTML for a requested page and sends the rendered HTML to the browser.

In SSR, the server processes the request, prepares the required data, renders the page, and returns HTML. The browser displays the returned page. JavaScript may subsequently add interactivity through hydration or other client-side code.

Benefits:

1. Improved initial rendering: The browser can display meaningful HTML before all client-side JavaScript has downloaded and executed.
2. Search engine optimization: Search engine crawlers can more easily access content already present in the HTML response, although indexing depends on the crawler and application.

Other acceptable benefits include improved initial content visibility, accessibility, and support for clients with limited JavaScript execution capabilities.

### Q8(b). Write a program to demonstrate SSR using Node.js or Python. (10 Marks)

The following is one acceptable solution using Node.js and Express.

Program: `server.js`

```
// Import Express to create the web server.
const express = require("express");

const app = express();
const PORT = 3000;

// Sample data that the server will render into HTML.
const student = {
    id: 101,
    name: "Amit",
    course: "BCA"
};

// Generate HTML on the server for the requested page.
app.get("/", (req, res) => {
    const html = `
        <!DOCTYPE html>
        <html lang="en">
        <head>
            <meta charset="UTF-8">
            <title>Student Details</title>
        </head>
        <body>
            <h1>Student Details</h1>
            <p>ID: ${student.id}</p>
            <p>Name: ${student.name}</p>
            <p>Course: ${student.course}</p>
        </body>
        </html>
    `;

    // Send the server-generated HTML to the browser.
    res.status(200).type("html").send(html);
});

// Start the HTTP server.
app.listen(PORT, () => {
    console.log(`Server running at http://localhost:${PORT}`);
});
```

Execution:

```

npm init -y
npm install express

# Start the server.
node server.js
```

Open `http://localhost:3000` in a browser. The browser receives HTML generated by the server, displaying the student's details.

Why this demonstrates SSR: The server constructs the HTML using student data before sending it to the browser. The browser does not need to build the entire page from a client-side JavaScript data structure.

A Python implementation using Flask and a server-side template engine such as Jinja2 is equally acceptable.

The following Express application defines two routes:

const express = require("express");

const app = express();

    { id: 1, name: "Amit", course: "BCA" },

                <tr><th>ID</th><th>Name</th><th>Course</th></tr>

        </body>
        </html>

    res.status(200).type("html").send(html);

// Start the server.
app.listen(PORT, () => {
    console.log(`Server running at http://localhost:${PORT}`);

Append the following code to `student-db.js`:

```
async function performCRUD() {
    try {
        // Connect before accessing the database.
        await connectDB();

        // Create: Insert a student document.
        const student = await Student.create({
            name: "Amit",
            email: "amit@example.com",
            course: "BCA"
        });

        // Read: Retrieve the inserted student.
        const foundStudent = await Student.findById(student._id);
        console.log("Read:", foundStudent);

        // Update: Change the student's course.
        const updatedStudent = await Student.findByIdAndUpdate(
            student._id,
            { course: "MCA" },
            { new: true, runValidators: true }
        );
        console.log("Updated:", updatedStudent);

        // Delete: Remove the student document.
        await Student.findByIdAndDelete(student._id);
        console.log("Student deleted");
    } catch (error) {
        console.error("Database operation failed:", error.message);
    } finally {
        // Close the connection after the demonstration.
        await mongoose.disconnect();
    }
}

// Execute the CRUD demonstration.
performCRUD();
```
